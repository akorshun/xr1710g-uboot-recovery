# XR1710G: переход на U-Boot с HTTP-рекавери

Скрипты для замены загрузчика на XR1710G (Airoha AN7581, он же Gemtek/econet
`xr1710g-ubi`) на сборку **[YYH2913/http-uboot](https://github.com/YYH2913/http-uboot)**
(релиз `xr1710g_260805`): 10GbE, веб-рекавери со встроенным DHCP и выбором
раскладки UBI, автоматический вход в рекавери при неудачной загрузке.

Рассчитано на роутер, который уже работает на OpenWrt/iStoreOS с разделами
`vendor` / `chainloader` / `ubi` (раскладка UBI 2.0), то есть на устройство со
сторонним загрузчиком в слоте `chainloader`, а не на заводскую прошивку с
разделом `tclinux`.

## Почему не «прошить из системы»

Слот загрузчика в работающей системе закрыт на запись: в `/proc/mtd` у
`chainloader` стоит `flags=0x0` (без `MTD_WRITEABLE`), запись в `/dev/mtd1`
возвращает `Permission denied`, а `kmod-mtd-rw` для ядра таких сборок в
репозиториях нет. Поэтому загрузчик пишется **через веб-рекавери самого
U-Boot**, а скрипт на роутере только приводит устройство в это рекавери:

```
flash.sh на роутере            рекавери на http://192.168.255.1
  проверки и копия слота  -->  POST /upload/uboot  -->  запись слота
  bootcmd=http_recovery        (upload.sh / upload.ps1)   + очистка ubootenv
  reboot
```

После успешной записи рекавери само стирает `ubootenv` и `ubootenv2`, поэтому
`bootcmd` возвращается к заводскому значению и роутер снова грузит систему —
уже новым загрузчиком. Прошивка, настройки и данные при этом не стираются.

## Шаг 1. На роутере

```bash
wget -qO- https://raw.githubusercontent.com/akorshun/xr1710g-uboot-recovery/main/flash.sh | sh
```

Что делает `flash.sh`:

| Проверка / действие | Подробности |
| --- | --- |
| модель | `econet,xr1710g-ubi` из `/tmp/sysinfo/board_name` или DT |
| слот | раздел `chainloader` ровно 1 МиБ |
| текущий загрузчик | версия U-Boot из дампа слота |
| **умеет ли рекавери** | в слоте есть `HTTP recovery server listening`, иначе отказ |
| раскладка UBI | по адресу конца раздела `ubi`: 2.0 / 1.5 / 1.0 |
| окружение | `/etc/fw_env.config`, наличие томов `ubootenv`/`ubootenv2` |
| резервная копия | `/root/xr1710g-chainloader-<дата>.bin` + sha256 |
| запись | `bootcmd=http_recovery` одним пакетным `fw_setenv -s`, с проверкой чтением |
| перезагрузка | после подтверждения |

Опции: `-y` без вопросов, `-n` не перезагружать, `-b` вообще не трогать флеш
(только проверки, копия слота и инструкция по входу кнопкой), `-r` вернуть
заводской `bootcmd`.

Копию слота стоит забрать на ПК до перезагрузки:

```bash
scp root@192.168.50.1:/root/xr1710g-chainloader-*.bin .
```

## Шаг 2. С ПК

Роутер поднимет рекавери на `http://192.168.255.1` и сам выдаст ПК адрес
`192.168.255.2` по DHCP (сетевая карта — в автоматическом режиме, кабель в порт
10GbE). Дальше либо веб-интерфейс («Update U-Boot» → файл →
`Upload and Recover`), либо скрипт:

```bash
curl -fsSLO https://raw.githubusercontent.com/akorshun/xr1710g-uboot-recovery/main/upload.sh
sh upload.sh
```

Windows:

```powershell
irm https://raw.githubusercontent.com/akorshun/xr1710g-uboot-recovery/main/upload.ps1 -OutFile upload.ps1
.\upload.ps1
```

Скрипты сами скачают `xr1710g-chainloader-slot.bin`, проверят sha256 и
legacy-заголовок uImage, дождутся рекавери, отправят образ
(`POST /upload/uboot`, `Content-Type: application/octet-stream`), покажут
прогресс стирания и записи и подтвердят завершение, после чего роутер
перезагрузится.

Ручной вариант той же отправки:

```bash
curl -X POST --data-binary @xr1710g-chainloader-slot.bin \
  -H 'Content-Type: application/octet-stream' \
  http://192.168.255.1/upload/uboot
```

## Вход в рекавери кнопкой (без изменения флеш-памяти)

Если не хочется трогать окружение U-Boot — `sh flash.sh -b` и затем:

1. ПК в порт 10GbE, сетевая карта в режиме DHCP.
2. Выключить роутер, включить и, когда замигает индикатор порта 10GbE, нажать и
   держать `reset`.
3. Отпустить, когда индикатор состояния сменит ровный красный на «бегущий»
   рекавери-режим. Запас по времени большой — если не уверены, подождите ещё
   несколько секунд.
4. Открыть `http://192.168.255.1`.

Кнопка работает и в заводском/стороннем загрузчике, и в новом: оба выводят в лог
`Recovery button detected, starting web recovery...`.

## Прошивка системы тем же рекавери

Тот же веб-интерфейс умеет писать `*-sysupgrade.itb` в том `fit`, полностью
пересоздавая UBI:

```bash
sh upload.sh -t firmware -l 2.0 -f openwrt-...-xr1710g-squashfs-sysupgrade.itb
```

Раскладка выбирается **по DTS заливаемого образа**, а не по текущей:

| Выбор | Раздел | Размер | Конец |
| --- | --- | --- | --- |
| UBI 2.0 | `ubi` | 439 МиБ | `0x1be00000` |
| UBI 1.5 | `ubi1.5` | 473,75 МиБ | `0x1e0c0000` |
| UBI 1.0 | `ubi1.0` | 503 МиБ | `0x1fe00000` |

Ошибка в выборе не ломает загрузчик, но Linux может бесконечно ждать
`/dev/fit0`. При заливке прошивки стираются система, overlay, установленные
пакеты и сохранённое окружение U-Boot; заводские MAC и EEPROM восстанавливаются
из вендорного региона DSD.

## Откат

* Залить в рекавери сохранённую копию слота (`/root/xr1710g-chainloader-*.bin`)
  через тот же `uboot`: `sh upload.sh -f xr1710g-chainloader-<дата>.bin`.
  Это тоже очистит окружение, то есть вернёт и обычную загрузку.
* Если система ещё работает и `bootcmd` уже переписан, а рекавери не нужно:
  `sh flash.sh -r`.

## Как это устроено внутри

Разбор обоих загрузчиков (стороннего `xr1710g-wiro-recovery` и нового
`2026.07-00766-g53b73174c0fc`):

* Слот `chainloader` (1 МиБ по смещению `0x600000`) — это legacy-uImage-шим с
  корректными CRC, а по смещению `0x2100` лежит FIT со второй ступенью U-Boot.
  Рекавери проверяет и magic, и CRC, поэтому `u-boot.bin` или `*.itb` в цель
  `uboot` заливать нельзя.
* Веб-рекавери: `GET /about` (версия, раскладка, `ui_build`), `GET /status`
  (прогресс), `POST /upload/uboot`, `POST /upload/firmware?layout=…`,
  у сборки wiro ещё `GET /status-ack/<generation>` для немедленной перезагрузки.
  Адрес всегда `192.168.255.1`, DHCP выдаёт `192.168.255.2`.
* Ключевое различие: у новой сборки `bootcmd=run boot_ubi || http_recovery`,
  то есть неудачная загрузка сама открывает рекавери. У стороннего загрузчика
  `bootcmd=run boot_ubi` без запасного варианта — поэтому «сломать» загрузку
  (например, переименовать том `fit`) нельзя: роутер останется в консоли U-Boot
  без сети. `flash.sh` вместо этого штатно ставит `bootcmd=http_recovery`.
* В сохранённое окружение пишутся только `bootcmd` и нейтральные переменные
  загрузки; `wiro_env_magic`/`wiro_env_schema`/`wiro_env_generation` не
  трогаются — они помечены в U-Boot как read-only, и попытка их переписать
  привела бы к отказу импорта окружения.
* Если сохранённое окружение всё же не будет принято загрузчиком, роутер просто
  загрузится как обычно — тогда остаётся вход кнопкой (`flash.sh -b`).

## Проверено

* Факты о разделах, инструментах и загрузчике сняты с живого XR1710G на
  iStoreOS `v1.4.0 r0+1-99598e539d`, ядро 6.18.41: `vendor` 6 МиБ,
  `chainloader` 1 МиБ, `ubi` `0x1b700000`, тома `fit` / `ubootenv` / `ubootenv2`
  / `factory` / `rootfs_data`, `/etc/fw_env.config` на `/dev/ubi0_1`
  и `/dev/ubi0_2`, `fw_setenv` с пакетным режимом.
* `tests/run.sh` — 62 проверки на фальшивом роутере (подменённые `/proc/mtd`,
  дамп слота, `fw_printenv`/`fw_setenv`, `reboot`) и на мок-рекавери; CI гоняет
  их под `dash`, `busybox sh` и `bash`, плюс shellcheck, разбор `upload.ps1`
  парсером PowerShell и проверку образа слота.
* Сам образ загрузчика в репозитории побайтово совпадает с ассетом релиза
  `xr1710g_260805` (CI сверяет это отдельной задачей).
* Полный проход на железе (перезагрузка в рекавери и запись слота) пока не
  выполнялся. Поэтому перед первым запуском забирайте копию слота на ПК и
  помните про вход кнопкой: даже если сохранённое окружение загрузчик не примет,
  роутер просто загрузится как обычно.
